# ADR-0003 — Single authoritative owner per concern; others call it through a port

- **Status:** accepted
- **Date:** 2026-09-16

## Context

The directive's guardrails forbid duplicated ownership of memory, scheduling,
policy, approvals, or workflow state (§2; plan §3), and §3.1 makes structured
state authoritative in the control plane, not in any harness. The plan's
responsibility table (plan §5) assigns each concern exactly one canonical owner
and names explicit non-owners (e.g. harness chat logs are not the episodic
record; OpenClaw automations are not the global workflow owner; Inngest is an
executor, not a source of truth for world state). The marker (plan §5):

> Rule enforced in code review: if two components can both do a thing, one is
> authoritative and the other calls it through a port. **[ADR-0003]**

## Decision

1. Adopt the plan §5 ownership table as binding: for every concern in the table
   there is exactly one canonical owner, and the "explicitly NOT owner" column
   is enforced.
2. Where a second component needs the same capability, it must call the
   authoritative owner through a port (`packages/adapters`), never reimplement
   or bypass it. This rule is enforced in code review.
3. Known instances this settles now:
   - working memory belongs to the active harness (Jehad OS does not persist
     sessions); OpenClaw memory is cache-only (T6);
   - procedural memory is `procedures/` in git with the typed loader/schema in
     `packages/core` — harnesses may cache read-only copies (review §16);
   - business-domain schedules live only in the Jehad OS scheduler; true local
     edge schedules stay with OpenClaw (tito) — ownership table governs (T8);
   - channel ingress/egress and devices run on the OpenClaw edge under Jehad OS
     grants — no direct iMessage/HA coupling inside the kernel;
   - model calls go through the ModelProvider port behind model-egress policy;
     domain code never calls a vendor directly;
   - workflow *semantics* belong to Jehad OS behind `WorkflowRuntime`;
     workflow *execution/checkpoint* state belongs to Inngest, replaceably.
4. When a new concern emerges, its owner is named in the ownership table before
   implementation, not discovered by duplication.

## Consequences

- No split-brain state across Jehad OS and harnesses; a single place to audit,
  back up, and reason about each concern.
- Harnesses stay replaceable peripherals (AGENTS.md); their stores are caches,
  never the system of record.
- Bypass paths (a harness executing a privileged action directly) are treated
  as threats and tested (T2, §40 item 19 test: the API rejects actions outside
  a grant, full stop).
- We explicitly decline: parallel policy engines in harnesses, harness-owned
   schedules for business logic, second audit trails, and any "both can do it"
   convenience duplication.
- Cost: every cross-boundary need must grow a port first; accepted.
