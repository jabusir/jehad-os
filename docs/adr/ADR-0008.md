# ADR-0008 — Inngest as the initial durable workflow runtime behind WorkflowRuntime

- **Status:** accepted (spike confirmed 2026-09-17)
- **Date:** 2026-09-16 (spike result recorded 2026-09-17)

## Context

The directive requires a durable workflow runtime with checkpointing, retries,
idempotency, long sleeps, external-event and human-approval waits,
cancellation, resumability, scheduling, child workflows, and observability —
naming Inngest and Trigger.dev as candidates and mandating a
`WorkflowRuntime` abstraction so the product stays replaceable (§11.9, §33).
The original plan challenged this with a pg-backed-first runtime (old D1); the
owner's external review rejected that: the stated premise (self-hosting needs
Docker/K8s) was factually stale for Inngest, and the planned M3 feature list
(persisted steps, signals, approval waits, cron, crash recovery, resume) is
already "the beginning of a bespoke workflow engine" whose hidden tail
(retry policy, backoff, leases, dead-letter, poison jobs, versioning, timer
correctness, cancellation, concurrency, fan-out/fan-in, step idempotency,
side-effect replay, migration, introspection, history) we must not rebuild
(review §2, D1 superseded). The review requires a minimal spike before this
ADR is finalized (review §2; plan §15 M3). The final-cleanup review adds:
Inngest is execution, not necessarily a long-running worker daemon; no
process-topology assumptions in `packages/core` (cleanup §6). The marker
(plan §12):

> **[ADR-0008] Use Inngest as the initial durable workflow runtime behind the
> `WorkflowRuntime` boundary.**

## Decision

1. Use Inngest as the initial durable workflow runtime, entirely behind the
   `WorkflowRuntime` interface: `start(workflow, input) → WorkflowHandle ·
   signal(handle, signal) · cancel(handle) · status(handle) → WorkflowStatus`
   (§11.9, retained). The interface lives in `packages/adapters`; the
   implementation in `packages/workflow/inngest`; no Inngest imports outside
   `packages/workflow` (M3 criterion; ADR-0002).
2. Local development uses the Inngest dev server (single CLI command; no
   Docker/K8s). Jehad OS PostgreSQL remains authoritative for world state,
   domain state, evidence, audit, permissions, decisions, commitments, and
   events. Inngest owns workflow execution/checkpoint state only — an
   executor, never a source of truth; the canonical event ledger is not
   duplicated inside Inngest. Execution flow: Jehad OS event → workflow
   dispatch → Inngest execution → Jehad OS state mutation through domain
   services only (plan §12).
3. Managed vs self-hosted deployment is deferred to escalation E2. No
   process-topology assumptions in `packages/core`: `apps/worker`'s documented
   responsibility is registering/serving workflow functions and runtime
   integration required by the selected Inngest deployment model — not a
   baked-in always-on queue-daemon assumption (cleanup §6).
4. **Spike gate (first task of M3, before this ADR is finalized):** prove with
   the Inngest dev server — start workflow → persist step → terminate
   app/worker → restart → resume → wait for external signal → signal →
   complete. Record the spike result in this ADR before proceeding.
5. **Fallback protocol:** if the spike (or later operation) fails an *actual*
   requirement, return to the owner with the specific blocker before
   considering any hand-built runtime. "Postgres is already installed" is
   never a reason to write our own engine. The bespoke-engine feature list
   above is exactly what we choose not to rebuild.
6. Future upgrade path: if Inngest later fails a demonstrated requirement, the
   replacement lands behind the same interface.

## Spike result (M3 gate — recorded 2026-09-17)

**Verdict: PASS — ADR-0008 finalized as accepted.** The decision-4 protocol
(start → persist step → terminate app/worker → restart → resume → wait for
external signal → signal → complete) passes cleanly. A harsher variant
(executor killed with `kill -9` too) also passes on the durable self-hosted
shape. No actual requirement failed; no escalation. Evidence lives in
`packages/workflow/spike/` (throwaway scaffolding, clearly quarantined);
machine-readable report: `packages/workflow/spike/.run/report.json`.

**Versions:** inngest JS SDK 4.20.0 · inngest-cli 1.44.0 (both `dev` and
`start` modes) · Node 22.23.2 · macOS (darwin, arm64) · Redis 8.10.1 via brew
(scenario B only). Timings below are from the recorded run
(2026-09-17, `spike/.run/report.json`).

### Scenario A — official gate: `inngest dev`, kill -9 the app/worker only

The protocol exactly as written in decision 4. All steps PASS:

| --- | --- | --- |
| start dev server (`npx inngest-cli@1.44.0 dev -p 8288 -u <serve-url> --persist`) | PASS | ~0.8s to healthy |
| start worker (serves the function over `node:http` via `inngest/node`) | PASS | ~0.3s; registration `function_count: 1, mode: dev` |

| terminate app/worker — `kill -9` worker process group, verified dead | PASS | ~0.5s |

| resume — persist-step NOT re-executed (executor-held checkpoint memoized) | PASS | marker still exactly 1 line |
| wait for external signal (parked at `waitForEvent`) | PASS | run state in executor |
| signal (event sent post-restart) | PASS | — |
| complete — finalize step ran, `signal=received`, run status Completed | PASS | signal→complete ≈260ms; 2 invocations total, persist-step executed exactly once (memoization held across the crash) |

### Scenario B — harsher variant: `inngest start` + external Redis, kill -9 executor AND worker

Same sequence, but the executor (single self-hosted binary) and the worker are
both SIGKILLed; Redis (external, brew — no Docker) holds queue/run state,
SQLite holds history. All steps PASS: persist-step executed exactly once
across the full crash (resume invocation replayed with memoization);
`signal=received` completion ≈0.5s after signal (restart-to-resync ≈5.8s).
**This is the concrete durable local/self-hosted runtime shape** (see below).

### Scenario C — negative control: `inngest dev`, kill -9 executor AND worker

CONFIRMED limitation (not a gate failure): the dev server's in-flight run
state (waitForEvent pauses, timers, queue) is in-memory and dies with the
process; `--persist` only persists history/events to SQLite. After a dev-server
kill -9, a parked run is stranded — neither a post-restart signal nor the
overdue wait timeout completes it. Architecturally tolerable by the authority
split (decision 2 / plan §12: losing executor state costs in-flight executions
only; canonical state is re-driven from the outbox) — but it means **the dev
server is a dev convenience, never the durable executor**.

### Concrete dev/runtime shape (output of this spike, per cleanup §6)

- **Serving mode:** app-hosted HTTP serve endpoint. `packages/workflow` serves
  Inngest functions via the SDK's `inngest/node` adapter (plain `node:http`,
  zero extra deps); the executor syncs it by URL (`-u`). `apps/worker`'s
  Phase-1 shape is therefore "host the serve endpoint and register functions"
  — not a bespoke queue daemon — exactly the revised responsibility sentence.
- **Local development:** `npx inngest-cli@latest dev -p 8288 -u <serve-url>`
  (single CLI command, no Docker/K8s). Caveats: run `--persist` to keep
  event/run history across dev-server restarts, and accept that in-flight
  runs do not survive a dev-server restart (scenario C).
- **Durable local/self-hosted (validated in scenario B; input to E2, not a
  commitment):** `inngest start` single binary + external Redis (run state) +
  SQLite or PostgreSQL (history) — survives kill -9 of everything except the
  durable stores. No Docker required.
- **Managed vs self-hosted:** still deferred to escalation E2.

### Friction and findings (inputs to the M3 adapter work, none blocking)

1. **Dev server run state is not durable** (scenario C above). Known upstream
   shape: `--persist` covers SQLite history only; queue/run state lives in an
   embedded in-memory Redis (CLI exposes `--redis-uri` on `inngest start`
   only).
2. **waitForEvent `if` matchers:** dev server 1.44.0's expression compiler
   rejects `data.*` references in waitForEvent `if` filters
   (`InvalidExpression: undeclared reference to 'data'`), failing the run.
   The spike omits the filter. The adapter (W1 signal vocabulary) must not
   rely on `if`-filtered waits against the dev server; re-check on
   cloud/self-hosted at adapter time.
3. **SDK v4 API notes:** functions via `inngest.createFunction`; serving via
   subpath adapters (`inngest/node` returns an `http.RequestListener`);
   unsigned local dev requires `INNGEST_DEV=1`; `client.send()` returns EVENT
   ids — run ids/status come from `GET /v1/events/{eventId}/runs`.
4. **Misleading status label:** the dev server's events/runs API reports
   `"Completed"` for an attempt parked at a wait; wait-state must be detected
   from step/pause history (or the platform run API), not that label — a
   concrete input for `WorkflowStatus` mapping (W1).
5. First `npx inngest-cli@latest` download takes ~30s (cache afterwards);
   scenario B needs a local `redis-server` (brew).

## Consequences

- Durable execution (kill -9 recovery, approval waits surviving restart, cron,
  signals) is bought, not built; kernel engineering concentrates on domain
  semantics.
- This ADR's status was "accepted, pending M3 spike confirmation" until the
  spike result was recorded here; the spike passed and M3 finalized it as
  accepted (see Spike result, 2026-09-17), satisfying plan §1 exit criterion 3.
- Two state stores exist (Postgres canonical, Inngest execution); the boundary
  is strict and already drawn, and workflow state is expendable/replaceable.
- We explicitly decline: a bespoke durable-workflow engine (only on a
  demonstrated, owner-confirmed Inngest blocker — plan §16), Inngest
  primitives in domain code, and any Inngest copy of canonical state.
- M3 acceptance: kill -9 mid-workflow → worker restart resumes; approval pause
  survives restart; no Inngest imports outside `packages/workflow`.
