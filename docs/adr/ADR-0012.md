# ADR-0012 — Model/data egress policy enforced before provider dispatch

- **Status:** accepted
- **Date:** 2026-09-16

## Context

The directive's security architecture separates untrusted input from the
action layer and requires that sensitive content never casually reaches models
(§26.1); secrets must never enter prompts (§26.5; T4); employer and financial
data have hard boundaries (§4). The external review found a bare
`call_model` capability too coarse: the real question is whether *this data*
(domain × sensitivity) may leave for *this provider/model* — critical for
employer data, financial data, sensitive personal content, future medical
records, credentials, and client data (review §7). Model egress violation is
threat T12 (review §24). The marker (plan §9):

> **[ADR-0007]** (extended), **[ADR-0009..0012]**.

## Decision

1. Adopt `ModelEgressPolicy {domainId, sensitivity, allowedProviders,
   allowedModels?, allowRemote, requireRedaction}` (review §7). Plan §9
   examples: `personal.normal` → OpenRouter allowed; `finance.sensitive` →
   selected providers only; `work.remote-employer` → personal model providers
   forbidden; `secret` → never in model context.
2. Context building calls policy **before** provider dispatch. A denial
   raises and is audited before any model call occurs; never rely on prompts
   saying "don't expose this."
3. The `ModelProvider` port is egress-gated (plan §4.1): every `model_calls`
   row implies the egress-policy check passed (denials raise + audit before
   any dispatch — plan §7).
4. The check composes with, and is separate from, the `call_model:<provider>`
   capability (ADR-0007): the grant says the run may call a provider; the
   egress policy says this data may go there. Both must pass.
5. The same data-centric rule feeds memory promotion gate 3 (ADR-0004): the
   data's domain/sensitivity must permit the provider being asked.

## Consequences

- Sensitive domain content cannot reach an unauthorized provider even when a
  run holds a model capability; M4/M5 acceptance — finance/work-sensitive
  context + unauthorized provider → denied before the model call, plus an
  egress-denial hermetic test in `pnpm test` (plan §13).
- `work.remote-employer` interacts with DomainBackend modes (ADR-0010):
  remote-domain content never transits personal providers (T15).
- Policy is data (configuration), so tightening for a future employer is an
  edit, not a code change.
- We explicitly decline: prompt-based secrecy requests, provider-side
  "trust us" filtering as the control point, egress checks after dispatch,
  and any path from domain code directly to a vendor SDK (ADR-0002).
- Redaction machinery (`requireRedaction`) is a policy field now; concrete
  redaction implementations land when a policy first requires them.
