# ADR-0007 — Capability grants with verifiable possession (token claims, hash-stored)

- **Status:** accepted
- **Date:** 2026-09-16

## Context

The directive mandates capability-based permissions — grants per task, least
privilege, agents disposable, capabilities controlled (§26.2) — with human
approval gates for high-risk categories (§26.3) and an audit trail that can
reconstruct which permissions an action used (§26.4). The external review found
the plan's grant concept right but the possession mechanism vague: trusting a
caller-supplied `grantId` is not verification; grants must not be "just database
metadata" (review §5). The marker (plan §9, extended):

> Grants are revoked on run end. **[ADR-0007]** (extended), **[ADR-0009..0012]**.

## Decision

1. Deny by default. A run acts only through `capability_grants` issued at
   dispatch to a principal/run with shape `{capability, resource, domainId,
   expiresAt}`. Capability vocabulary v1: `read_events`, `write_entity:<type>`,
   `call_model:<provider>`, `send_channel:<id>`, `spend_budget:<usd>`,
   `act:<provider>`.
2. Possession is proven by an opaque random capability token with claims:
   principal, run_id, capability, resource, domain, expires_at, nonce. The
   token is short-lived, scope-limited, revocable, auditable,
   non-escalatable, and unusable outside the granted resource/domain. The
   canonical grant row stores only a `token_hash` (plan §7).
3. Exact signing/rotation machinery is Phase 2+; the token primitive itself
   ships in Phase 1 (M4) so grants are never trusted from a caller-supplied id.
4. Autonomy ceiling per action type comes from versioned `policy.yaml` (the §35
   pattern): v1 ships `read: autonomous · propose: autonomous ·
   write_canonical: gated · external_side_effect: approval_required ·
   money_and_contracts: prohibited`.
5. Policy evaluation happens only in Jehad OS; edge harnesses (OpenClaw)
   receive time-boxed, single-purpose grants they cannot escalate — the API
   rejects actions outside the grant, full stop (§40 item 19 test). Grants are
   revoked on run end.

## Consequences

- Grant-less or out-of-scope actions fail closed and are audited; M4
  acceptance: grant-less action → 403 + audited; token outside its scope
  rejected.
- A stolen grant id without the token proves nothing; a token outside its
  scope/domain/expiry proves nothing.
- Slight ceremony on every dispatch (mint, deliver, hash, verify, revoke) —
  accepted; cost is confined to dispatch time.
- We explicitly decline: trusting caller-asserted grant ids, ambient authority
  from principal identity alone, permanent broad capabilities attached to
  agent identities, and harness-side policy evaluation (T2).
- Egress-capability checking (`call_model:<provider>`) composes with the data
  egress policy in ADR-0012; both must pass.
