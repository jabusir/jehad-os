# ADR-0010 — DomainBackend storage modes (local/remote/federated/opaque)

- **Status:** accepted
- **Date:** 2026-09-16

## Context

The directive requires hard data boundaries (§4) and employer-specific state
capable of remaining entirely on employer infrastructure — "intelligence comes
to the data" (§4.3, §4.4) — with one control plane over many bounded domains
(§3.4). The external review found logical isolation via `domain_id` in one
Postgres insufficient for a future employer that may require no personal-DB
copies and employer-approved models only, and required a DomainBackend /
storage-mode concept (review §3). The final-cleanup review tightened the mode
semantics — opaque means zero domain-content export by default; sanitized
counts like "2 work decisions need review" belong to federated (cleanup §3) —
and required that cross-domain composition be policy-mediated rather than
audit-only (cleanup §4). The marker (plan §10):

> … **[ADR-0010: DomainBackend storage modes]**

## Decision

1. A domain is **not synonymous with a row-level partition in the personal
   PostgreSQL database.** Each domain declares a `storage_mode`:
   - **local** — canonical domain data may live in Jehad OS PostgreSQL (v1:
     personal, finance, research, learning, creative, and current-startup work
     if authorized);
   - **remote** — canonical state remains in the remote environment; Jehad OS
     interacts only through a `DomainBackend` adapter and may receive
     responses allowed by policy;
   - **federated** — a deliberately defined, sanitized subset of metadata may
     cross the boundary while sensitive details stay remote (e.g. "2 decisions
     need review", "1 approval pending", "adapter healthy") (cleanup §3);
   - **opaque** — zero domain-content export by default: personal Jehad OS may
     know only that the domain/capability exists, plus adapter health and
     capability availability if policy permits; it must not assume counts,
     titles, summaries, deadlines, project names, or decision metadata may
     cross; no semantic payload crosses unless the domain's policy is
     explicitly changed (cleanup §3).
2. Establish the `DomainBackend` interface now (id, mode, query, context,
   capabilities, health — plan §10) with these invariants; concrete remote
   backends are NOT implemented in Phase 1 (review §22/§27 — minimal
   abstraction only). All six v1 domains run `storage_mode=local` (A16).
3. A fake adapter at M4 proves the invariant per cleanup §3: a fake
   federated domain exports only policy-defined sanitized metadata; a fake
   opaque domain exports no semantic payload at all — personal Postgres
   receives nothing but existence/health (review §25).
4. Within local domains, `domain_id` is enforced on every read/write path in
   the data layer, not by model discipline. Work domain: `detachable=true`,
   excluded from personal semantic promotion (ADR-0004 gate 2), exportable +
   deletable as a unit, never crosses into another domain's context package.
   Finance rows carry stricter sensitivity defaults and egress policy
   (ADR-0012).
5. Cross-domain composition (cleanup §4): raw cross-domain data access is
   denied by default; composition happens only through an explicit,
   policy-mediated aggregation layer (conceptually
   `CrossDomainQueryPolicy.mayRead(principal, sourceDomain, requestedFields,
   purpose)`) requesting the minimum necessary projection from each domain;
   for remote/federated/opaque domains the `DomainBackend` controls what
   projection may leave the boundary. Invariant: composition is explicit,
   policy-gated, least-data, provenance-preserving; raw arbitrary cross-domain
   joins are forbidden.
6. Context-package design, memory-promotion rules, and the future
   HarnessAdapter all consult the DomainBackend boundary.

## Consequences

- The architecture can honestly support "data stays where it belongs;
  intelligence comes to the data," including managed-machine employer
  constraints (T15) — without building federation infrastructure now.
- The M4 fake-adapter test makes the isolation invariant executable, not
  aspirational.
- The goal is controlled composition, not "never compose" — e.g. a future
  "what needs my attention today" view may combine counts/items across
  domains via the aggregation layer only.
- We explicitly decline: any concrete remote DomainBackend (interface + fake
  adapter only until a real employer boundary exists — plan §16), a
  sophisticated cross-domain federation/query engine in Phase 1 (invariant
  recorded; engine deferred — cleanup §4), graph databases, and treating
  `domain_id` filtering as sufficient for non-local domains.
