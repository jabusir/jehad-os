# ADR-0005 — Schema v1 scope (minimal, review-§23-revised)

- **Status:** accepted
- **Date:** 2026-09-16

## Context

The directive warns against building the full §5 world model upfront and
sketches a phased build (§32); the external review's schema item (review §23)
required a minimal v1 that nonetheless adds a few concepts early — principals,
relationships/dependencies, human_waits, action_intents/attempts, possibly a
minimal evidence primitive — to prevent architectural dead ends, while
normalizing decision assumptions into one canonical table (review §10) and
adding metadata concepts (`events.schema_version`, `domains.storage_mode`,
`artifacts.storage_backend`, assertion provenance kind). Temporal validity is
added per-entity only where it matters (review §19). The final-cleanup review
further required the principals table to land at M0 via a bootstrap migration
so the API never exists unauthenticated (cleanup §2). The marker (plan §7):

> … `relationships` and `evidence` carry them in v1; no blanket column
> spraying. **[ADR-0005: schema v1 scope, revised]**

## Decision

1. Schema v1 is exactly the table set of plan §7 — no more: `principals`
   (M0 bootstrap migration `000_bootstrap_auth.sql`), `domains`, `events`,
   `outbox`, `entities`, `commitments`, `decisions`, `assumptions`,
   `relationships`, `evidence`, `memory_candidates`, `procedures` (index rows;
   bodies are files), `runs`, `human_waits`, `artifacts`, `action_intents`,
   `action_attempts`, `capability_grants`, `audit_log`, `escalations`,
   `model_calls`. Entities from §5 not listed are Phase 2+.
2. Include the review-§23-driven shapes, not merely names:
   - `decisions.assumptions` jsonb is removed; the `assumptions` table
     (decision_id, statement, status held/violated/unknown, last_checked_at) is
     the single source of truth (review §10);
   - blocking is expressed via `relationships` (relation `blocked_by`), not
     `blocked_by[]` arrays (review §9); no graph database — first-class edges
     in Postgres;
   - `events.schema_version int` (review §18), `domains.storage_mode`
     (ADR-0010), `artifacts.storage_backend` (postgres default / file /
     object-later; Phase 1 = Option A, small textual artifacts in Postgres so
     pg_backup covers them — review §11, T16);
   - `human_waits` raw intervals; `human_blocked_ms` is a derived projection,
     not a column on `runs` (review §14);
   - `action_intents.status` (proposed/approved/prepared/cancelled) and
     `action_attempts.outcome` (executing/succeeded/failed/unknown/reconciled)
     with one canonical owner per state (cleanup §5);
   - `capability_grants.token_hash` (ADR-0007); minimal `evidence` primitive
     (review §20).
3. Temporal validity (`valid_from`/`valid_until`/`observed_at`) exists only on
   `relationships` and `evidence` in v1; no blanket column spraying (review §19).
4. Every table carries `domain_id` + `sensitivity` where the directive requires
   provenance (§5); no generic jsonb "memory" table.
5. Landing order: `000_bootstrap_auth.sql` at M0 (principals only); the
   remaining schema-v1 migrations at M1, with a tested down path per migration
   (AGENTS.md).

## Consequences

- Phase 1 can build the personal-ops slice without schema churn, while the
  early concepts (relationships, evidence, action semantics, auth) avoid
  expensive later migrations.
- Leverage and blocked queries run on the `relationships` graph
  deterministically (plan §13; review §25).
- Backup/restore has a single backup domain (Postgres rows + artifact content
  verified in the M1 practiced restore).
- We explicitly decline: pgvector/semantic retrieval, a graph database, a
  generalized ontology, and any §5 entity not in the v1 list (plan §16).
- Schema growth beyond v1 is a new migration set plus (if structural) a new
  ADR.
